# Verified CUSTOMER onboarding (V23)

## Why this replaces the former enrollment flow

The legacy account enrollment let staff supply a password and later enabled an account after an unrecorded identity check. Neither staff-supplied secrets nor an OWNER role by itself proves a garage customer's identity. V23 adds non-document identity-proof metadata to the account and a one-use customer-controlled initial-password challenge. The backend **rejects CUSTOMER authentication, including legacy mistakenly enabled accounts, unless both proof and customer-chosen initial password are recorded**.

## Staff enrollment flow

1. Trusted OWNER or individually delegated CASHIER creates an **existing ACTIVE Customer** identity via `POST /api/customer-accounts`, with `{"customerId":12,"username":"customer.one"}`. This creates a **disabled** account with a random cryptographically generated, unknown placeholder password hash. **The enrollment request has no password property.** Staff never choose or read the customer's initial secret.
2. OWNER personally verifies the claimant against the pre-existing garage Customer record **in person** (approved physical government-ID verification procedure, document authenticity and face match, reference kept in a separately controlled case system), confirms that the email on the Customer business record belongs to the claimant, and records the approved non-PII case reference via `POST /api/customer-accounts/{accountId}/verify-and-invite` with `{"caseReference":"CASE-00123"}`. Only OWNER + effective `customer:register` authority is accepted at both the JWT filter and service layer. A CASHIER with delegated registration **cannot** attest identity or send invitations.
3. The transaction records `customer_verified_at`, `customer_verified_by`, `customer_verification_ref` and `customer_verified_email`, revokes older tokens, and sends a 15-minute single-use token to the existing, verified Customer email through the configured TLS SMTP recovery service. The browser/customer never receives token material in API responses. If email delivery is unavailable the transaction fails and no verification/invitation is persisted. Reissuing an invite is throttled to once per minute. Raw identity documents, NIC, tokens and credentials must **not** be placed in the case reference, logs or audit event.
4. Customer visits the **client-owned HTTPS** setup page and posts `{"token":"<single-use-secret>","password":"<customer-chosen-strong-password>"}` to `POST /api/auth/recovery/initial-password`. The token is SHA-256 hashed in the database, stored only with 15-minute expiry and `INITIAL_PASSWORD` purpose, and is account-bound and credential-version-bound. It is consumed once; a reset or verify-email token cannot be substituted. Passwords must be between 15 and 72 Java characters, and no more than 72 UTF-8 bytes (BCrypt). Customer chooses the password without staff knowing it.
5. **Account remains disabled after password setup.** OWNER reviews the verified case and explicitly calls `PATCH /api/customer-accounts/{id}/activate`. The service rejects activation if proof is missing, customer email changed, account was not set up by the customer, Customer is inactive or actor is not OWNER. Only now can the customer log in with existing `POST /api/auth/login` and access `GET /api/customer/me`.

## Policy and deployment safeguards

- This implementation enforces an OWNER's auditable **attestation** and ownership of an email mailbox; **it cannot itself prove a person was physically identified**. A real garage-approved identity-proofing SOP, training, evidence custody, verification of business-customer email, privacy/retention rules and an authenticated client-facing HTTPS setup page are required before real customers are invited. A made-up case reference is not independent identity proof.
- SMS/provider delivery is NOT implemented. The recovery/initial-password sender is **disabled by default** (`app.recovery.enabled=false`); it must be configured with a reviewed TLS SMTP sender, a legitimate from address and fixed client-owned `app.recovery.page` HTTPS URL. Without this, invitations fail closed.
- Customer status SUSPENDED invalidates login, email changes invalidate the existing recorded proof, and password setup does not enable the account. All sensitive response paths use `Cache-Control: no-store`; token/setup failures return generic responses without disclosing the target account.
- Password recovery for already enabled accounts continues via existing verified recovery-email routes; initial-password tokens are a separate purpose and cannot be redeemed for ordinary password recovery.
- V23 adds CUSTOMER proof and initial credentials. **V23 has not been applied to shared Supabase.** CI verifies fresh V1–V23 and V1–V14 synthetic upgrade to V23 on disposable PostgreSQL. Read-only review also found `public.flyway_schema_history` in an exposed schema with RLS OFF and SELECT grants effective for browser roles. Because ALTERing Flyway's own history table inside a Flyway migration may block the migration lock, the separately approved DBA change is provided at `ops/security/lock-down-public-flyway-history.sql`, **not** as a V24 Flyway migration. It requires a verified backup, maintenance window, table-owner connection and no concurrent Flyway. No shared database SQL was executed.
- OWNER can manually attest through the API, so operational signoff of the proof verification workflow remains a release gate. Never mark Issue #32 fully resolved until this SOP and actual customer-facing setup page are approved.
